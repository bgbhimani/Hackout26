# Architecture & Phase Plan

## System architecture

```
┌─────────────────────┐        ┌──────────────────────────┐        ┌────────────────────┐
│  Next.js frontend    │  HTTP  │   FastAPI backend        │  SQL   │  PostgreSQL+PostGIS │
│  (React, TS, Tailwind)│──────▶│  api/ → services/ → models│───────▶│                     │
│  localStorage JWT     │◀──────│  JWT auth, role checks    │◀───────│  Geography columns  │
└─────────────────────┘  JSON  └──────────────────────────┘        └────────────────────┘
                                          │
                                          ├── ml/ (Phase 7): trained XGBoost model, loaded once at
                                          │   startup, never retrained per-request
                                          └── OR-Tools (Phase 6): route optimization, called
                                              synchronously from route_service.py
```

**Request flow example (Smart Matching, Phase 5):**
`Matching page → POST /api/matching/recommend → matching_service.py → PostGIS ST_Distance query
against Facility.location → scored, explained recommendations → Match rows persisted → JSON response`

## Database schema

See the table definitions in `backend/app/models/`. Summary of relationships:

```
User (auth only - not FK'd to generators/facilities in this MVP; role determines UI, not row ownership)

WasteGenerator ──< WasteRecord ──< Match >── Facility
                        │                        │
                        │                        ├──< Route ──< RouteStop >── WasteRecord
                        └──< CarbonRecord         │
                                                   │
WasteGenerator ──< Forecast (generator_id + waste_type, not tied to a specific WasteRecord)
```

Every location (`WasteGenerator.location`, `Facility.location`) is a PostGIS `GEOGRAPHY(POINT, 4326)`
column with a spatial index, enabling real `ST_Distance` / `ST_DWithin` queries for matching and routing
rather than application-level haversine math.

## Why certain technical choices were made

- **PostGIS `GEOGRAPHY` over `GEOMETRY`:** `GEOGRAPHY` computes `ST_Distance` in metres directly on a
  spherical model, which is what "distance to nearest facility" actually needs - no manual SRID
  projection step.
- **JWT in `localStorage`, not an httpOnly cookie:** simpler client-side auth flow, acceptable for an
  MVP with no server-rendered authenticated pages; documented here as a deliberate scope cut, not an
  oversight (Phase 10 "Limitations" will restate this).
- **Lazy database engine (`app/database/session.py`):** the FastAPI app must boot and serve `/health`
  even before a real `DATABASE_URL` exists, so local frontend/backend integration work isn't blocked on
  database provisioning.
- **One initial "enable postgis" migration, autogenerate for the rest:** `CREATE EXTENSION postgis` is
  not something SQLAlchemy models can express, so it has to be a hand-written migration that runs before
  any Geography column is created; every other table is autogenerated from the models to avoid manual
  schema drift.
- **GeoAlchemy2 auto-creates its own GIST spatial index** on every Geography column when a table is
  created - Alembic's autogenerate doesn't know this and proposes a *second*, duplicate `create_index`
  for the same index, which fails with "relation already exists". Every migration that adds a geography
  column has that duplicate line removed by hand (see the initial schema migration for the pattern) and
  needs `import geoalchemy2` added manually too - autogenerate detects the type but not the import.
- **`app/database/geo.py` centralises lat/lng ↔ PostGIS conversion.** It lives under `database/`, not
  `services/`, specifically so `app/models/waste_generator.py` and `app/models/facility.py` can import it
  for their `.latitude`/`.longitude` convenience properties without models depending on the services
  layer - Pydantic's `from_attributes=True` then reads those properties like any other field.
