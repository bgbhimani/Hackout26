# ML Methodology — Waste Forecasting

## Pipeline

```
ml/data/historical_waste_panel.csv (Demo / Synthetic Data)
        ↓ load_panel()          - drop missing/zero/negative quantities
        ↓ build_features()      - season, previous_quantity, rolling_avg_3, label-encode categoricals
        ↓ time-based split      - train: years < 2025, test: year == 2025
        ↓ RandomForestRegressor - baseline
        ↓ XGBRegressor          - final model
        ↓ evaluate_model()      - MAE, RMSE, R² on the held-out test set
        ↓ joblib.dump(...)      - models + encoders + feature column order saved to ml/models/
        ↓ ml/predict.py         - loads all of the above ONCE at import time
        ↓ backend/app/services/forecast_service.py - builds live features, calls predict.py
        ↓ POST /api/forecast    - returns {predicted_quantity_tonnes, confidence, model}
```

Run it yourself: `cd ml && python generate_training_data.py && python train.py`

## What's real vs. synthetic, stated plainly

The training panel (`ml/data/historical_waste_panel.csv`) is **Demo / Synthetic Data** — six years
(2020-2025) generated by extending the same calibrated generator archetypes used for the live demo seed
data (`backend/scripts/seed_demo_data.py`), which are themselves grounded in real research (Gujarat dairy
statistics, published crop residue-to-product ratios, real crop calendars — see
`data/ml-data-research.md`). Every generator's seasonal pattern (which months a crop residue type is even
possible) comes from the real Gujarat crop calendar; the year-over-year quantities are a synthetic but
bounded, realistic drift on top of that real pattern.

**This is disclosed everywhere the forecast is shown, never presented as trained on live/verified data.**

## Why a time-based split, not a random one

A random 80/20 split would put some months of 2025 in training and others in testing for the *same*
generator/waste-type series — since `previous_quantity` and `rolling_avg_3` are lag features built from
that same series, a random split leaks future information backwards into "past" features the model is
scored on, producing an artificially inflated test score. **Train on 2020-2024, test only on 2025** avoids
this entirely: every test-set prediction only ever sees features built from data that came chronologically
before it.

A separate leakage bug was caught and fixed during development: computing `rolling_avg_3` as
`grouped.shift(1).rolling(3).mean()` where `grouped` is a `SeriesGroupBy` returns a **plain Series** after
`.shift(1)`, so the subsequent `.rolling()` call runs over the concatenated global series, not per group —
bleeding one generator's tail values into the next generator's opening rolling average. Verified
empirically and fixed by using `.groupby(...).transform(lambda s: s.shift(1).rolling(3).mean())`, which
correctly resets at each group boundary.

## Feature engineering

| Feature | Source |
|---|---|
| `waste_type` (encoded) | Categorical, label-encoded, encoder saved and reused at inference |
| `generator_type` (encoded) | FARM / FOOD_INDUSTRY / MUNICIPALITY / INDUSTRIAL |
| `district` (encoded) | One of the five demo districts |
| `season` (encoded) | Derived from month: KHARIF (Jun-Oct), RABI (Nov-Mar), ZAID (Apr-May) - matches the real Gujarat crop calendar |
| `month` | 1-12 |
| `previous_quantity` | The prior period's actual quantity for this exact generator+waste_type series |
| `rolling_avg_3` | Mean of the prior 3 periods for that series |

## Results (current trained model)

| Model | MAE (tonnes) | RMSE (tonnes) | R² |
|---|---|---|---|
| Random Forest (baseline) | 10.09 | 15.00 | 0.959 |
| **XGBoost (final)** | **9.49** | **14.00** | **0.964** |

XGBoost genuinely outperforms the Random Forest baseline on held-out 2025 data — not a rigged comparison.
See `ml/models/metrics.json` for the exact numbers from the last training run.

**Honest caveat:** R² this high partly reflects that the synthetic generative process itself is smooth
(a bounded multiplicative year-drift plus bounded month noise) rather than proof the model has solved
real-world unpredictability. A real deployment against genuine multi-year utility data would very likely
see a lower R² — this is disclosed, not hidden, per the project's "do not claim scientifically exact" rule.

## Confidence score — what it actually is

XGBoost's point prediction has no native probability. Rather than fabricate a number, confidence is
computed from the **Random Forest's per-tree prediction spread** on the same input: when the forest's many
independently-trained trees agree closely, confidence is high; when they disagree, confidence is lower.
This is a real, inspectable ensemble-uncertainty signal (see `ml/predict.py::_rf_confidence`), always
labelled as an estimate, never as a probability of correctness.

## Known limitations

- Training data is synthetic, calibrated but not independently verified against real utility records.
- The confidence score reflects model agreement, not real-world volatility (weather shocks, policy
  changes, etc. are not modeled).
- Cold-start: a generator/waste-type combination with zero prior history cannot be forecast (the API
  returns a 422, not a fabricated guess) — see `forecast_service.py::generate_forecast`.
- District is parsed from the generator's address string (a known MVP simplification, documented in
  `forecast_service.py::_infer_district`) rather than stored as its own column.
